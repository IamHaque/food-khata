# HTTP vault lifecycle

Setup and password login unlock the existing UserVault and migrate account metadata, provider sessions, and existing archive identity headers by atomic replacement. Keys are held per browser session in process memory. Logout removes that session key; already submitted sync jobs keep a reference to the cipher capability and a session copy until completion (covered by test_outlives_session_and_discards_keys_at_end). Shutdown stops jobs and clears session keys. A restarted process requires password login before credential access, even with a valid persisted browser cookie.

Disable invalidates browser sessions, cancels jobs in the same application database, and deletes provider sessions. HTTP owner reset and stopped-server CLI recovery use the same reset primitive: delete provider sessions, clear unrecoverable phones, retain local account IDs, names, provider identity digests, archives and analytics, and create a fresh vault. Relinking the same provider identity reuses the account ID. Errors propagate rather than reporting successful recovery after a vault failure. Recovery is not a transaction spanning SQLite and filesystem; an I/O failure requires retry/recovery.

Adoption requires an unlocked vault. Account metadata and sessions are encrypted in place before copies are created, including preexisting legacy-backup folders left without an adoption marker. The live app.db and its SQLite sidecars stay in the root. Analytics is snapshotted with SQLite backup (including committed WAL data); the live legacy analytics database remains in place. A pending marker lets password login resume an interrupted adoption with the same owner ID and key. Setup/registration failures return an error; the committed owner remains available for password login and retry. On unlock, legacy metadata and sessions in the user folder and legacy-backup folders are migrated even without a completed adoption marker. Existing analytics databases and order archives are preserved. Atomic replacement does not promise forensic erasure, nor does this migrate independently created external backups.

Provider identifiers in account metadata are encrypted because providers may return phone numbers as IDs. App database initialization replaces existing `jobs.provider_id` values with SHA-256 identity digests; unlock also migrates any app databases in the user and legacy-backup folders. Unlock and adoption migrate the top-level `provider_id` of each account history archive to the same digest, including existing backups. Already digested identifiers are left unchanged. Resume retrieves the raw identifier from unlocked account metadata, not the job or archive header. SQLite updates are transactional with secure-delete enabled and a WAL truncate checkpoint is requested; a busy reader can prevent the checkpoint, and neither this nor atomic file replacement guarantees forensic erasure. A SHA-256 identity digest supports cross-user duplicate detection without another user's key and survives recovery. These digests are equality identifiers, not password hashes: low-entropy provider IDs can be guessed offline.

Approved scope (2026-11-10, DEC-021): encryption protects provider credentials and account metadata; analytics and archive order payloads may retain plaintext personal data. New analytics imports store only the last four phone digits for masked account labels. Existing analytics databases may retain previously imported full numbers. Order archives remain unencrypted and their order payloads may contain provider-supplied personal data, including phone numbers or tokens. The archive-header migration does not change those payloads. No analytics/order data is deleted to claim blanket disk phone absence.

## Validation for this slice

The synthetic migration test starts with a plaintext account, session, phone-like job ID and archive header, plus a preexisting legacy backup with its own app database. It injects an archive rewrite failure, retries unlock/adoption twice, verifies that raw IDs remain recoverable only through unlocked metadata, and checks both databases and archive headers for one digest. A full temporary-tree scan checks the synthetic phone and token in every file; archive order payloads are inspected separately and deliberately retain the synthetic phone. This scan is evidence for the tested paths and fixture, not forensic erasure or a claim about existing order payloads, legacy analytics, unrelated files, or external backups.

Real Uvicorn tests use a local synthetic provider and exercise rotating forwarded IP login throttling, logout during an active job, owner reset and disable cancelling active jobs without recreating provider sessions, access isolation in both directions and non-owner rejection, and cancelled partial import plus resume after restart and password login with pre-upgrade job and archive identifiers. Paused and needs-code expiry runs on the actual cleanup thread with a test-only one-second age and 50 ms interval; production retains its 24-hour age and 60-second interval. A paused running job may already have discarded its key; its stale paused record is also transitioned to interrupted by cleanup. Cancellation remains cooperative while a provider operation is in progress.

Only synthetic temporary data and FakeProvider were used. Existing analytics databases may retain full phone numbers, and independently created external backups are not migrated. No claim of overall acceptance or blanket disk erasure is made.

One earlier full verification reported a truncated pytest failure; the focused sync suite and subsequent full run passed.
